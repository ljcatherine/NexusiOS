# Nexus engineering rules

Make frequent focused commits with descriptive messages, as requested by the owner.
Read docs/README.md before extending scope. Never claim hardware or signing validation without evidence.
Use Keychain for credentials and pins. Never commit SSH private keys, passwords, P12/PFX certificates, or provisioning profiles. Keep local credentials in ignored, owner-only files; imported SSH credentials must remain in the iOS Keychain. Never disable SSH host-key or HTTPS validation.
Keep transport, domain models, and SwiftUI separate. No fabricated production telemetry.
Validate the SSH foundation before beginning later phases.
For each new PS5 test-title build, remove the previous test-title installation and reinstall the new build using supported launcher/system operations, rather than replacing its executable in place. Close the title first, preserve rollback files and shared models/settings, and never remove the original or unrelated titles.
Verify deployed file permissions as well as hashes: PS5 eboot.bin and sce_module/libc.prx must retain executable permissions (0755); normalize packaging modes before transfer and verify them after installation.
Preserve unrelated working-tree edits and never commit local signing assets or passwords. Commit focused code and documentation changes together, push through the configured remote, and report verified results. Do not use Codemagic or GitHub Actions for building, testing, or publishing Nexus. Build and validate iOS IPAs locally with the pinned xtool setup; use the local release script when publishing is intended. Keep the production bundle identifier fixed to `com.ljcatherine.Nexus`, verify IPA structure and executable, and distinguish successful packaging from installation/SSH acceptance.
Versioned GitHub Releases contain only unsigned IPA assets, checksums, and metadata. Derive the marketing version from `project.yml`, allocate build numbers above existing Nexus releases, and keep release titles, notes, and filenames explicit about unsigned status. Never import or access signing credentials for a build.
Advance the marketing patch version for each new release: `1.0.0` → `1.0.1` → `1.0.2`, while keeping the major and minor components fixed. `scripts/xtool-release.sh` computes the next patch from existing releases; `project.yml` defines the minimum patch and approved major/minor line. Never change either major or minor number unless the owner explicitly approves it. Only an approved major/minor change may use `NEXUS_ALLOW_VERSION_LINE_CHANGE=1`; document that approval. The owner approved the move from the 0.4 line to 1.0 for the first public release on 2026-11-11; the first 1.0 release needs `NEXUS_ALLOW_VERSION_LINE_CHANGE=1` once. Continue incrementing the independent monotonically increasing build number.
Opening a terminal from Dashboard, Devices or New session should navigate into the actual session, including initial host-key challenges and errors. Keep test assertions on observable user behavior.
